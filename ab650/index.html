01. Tenant, licences and recovery

A tenant is the organisation's Microsoft 365 environment. A licence supplies product entitlement. An administrator role supplies permission to change settings. Pay-as-you-go pays for eligible consumption. None of these alone proves that a user can use a feature. A custom domain is a name you control; verification proves ownership, while DNS records determine service routing.

Choose the exact object

For branding, distinguish Microsoft 365 organisational themes from Entra sign-in branding. Start in the relevant admin centre and check the preview as a normal user. Organisation profile, security and privacy settings are tenant settings; a user's profile is a different object. Record the original value and intended audience before a change. For domains, add the name, publish the requested ownership record and verify it. Plan service DNS separately: changing MX redirects incoming mail; a verification TXT record does not. Do not switch MX while mailboxes remain at the old provider.

Find the licensing fault

Use the Microsoft 365 admin centre's licensing views to inspect the product, group assignment and user error. Check available seats, the service plans selected, the user's usage location and conflicting plans. Group-based licensing processes direct user members; nested group membership does not supply licences. A blank usage location in group assignment can inherit the tenant's location, so blank alone is not evidence of failure. An explicit invalid location error is stronger evidence. For Copilot, Agent 365 and Copilot Studio, check that specific product's current licence and billing prerequisites. Do not reuse one product's rules for another. During a licensing-group move, confirm that the destination assignment has processed before removing the old source.

Diagnose health before changing configuration

Write down the affected service, people, locations and UTC time. Check Service health for a matching incident and configure notifications for the services and recipients you need. An incident's scope must match the symptom. For a branch-only problem, compare connectivity insights with an unaffected location: DNS, routing, latency and path changes are useful evidence. A green service page does not prove every network path works. Usage reports describe activity, not live availability. Escalate with correlated times and affected endpoints, rather than a screenshot of one slow page.

Prove recovery

Microsoft 365 Backup protects selected Exchange mailboxes, SharePoint sites and OneDrive accounts. Define the recovery point objective (acceptable data loss) and recovery time objective (acceptable recovery delay). Configure the workload policy, confirm the actual protection units and wait for recovery points. Activation is not instant. Select a point within the available recovery window and a supported restore destination. An original-location restore can replace live scoped content; use a permitted alternate destination for inspection where supported. Validate files, mail, metadata and access against the requirement. Retention, version history and an enabled backup policy do not demonstrate a successful restore.

Worked case

Requirement: 12 analysts need Copilot. Evidence: the licensing group has 10 direct users and a nested group with 2 more. All 12 already have their base services.

Decision: inspect the Copilot assignment for each user. Add the two intended users through a supported direct-membership design, then recheck processing and entitlement. The group total is not a licence-success count.

Recovery evidence: an enabled SharePoint policy protects Site A, but the missing file was on Site B. The relevant protection scope is wrong; do not promise a restore from Site A.

02. Mail, Teams and SharePoint boundaries

A workload contains resources and permissions. A shared mailbox, a Teams channel and a SharePoint site have different access models. The exam often gives a valid setting for the wrong resource. First name the resource, the acting person and the exact action.

Mailbox type and delegation

A user mailbox belongs to a user; a shared mailbox supports a common address such as helpdesk. Full Access lets a delegate open and manage a mailbox. Send As sends as that mailbox. Send on Behalf identifies the delegate. Opening successfully does not prove sending rights. A shared mailbox up to 50 GB generally needs no separate mailbox licence, but delegates need their own Exchange Online entitlement. A larger primary mailbox or features such as archive and hold can change licensing needs. Keep the backing account when converting a licensed user mailbox to shared. Check size and feature requirements before removing its licence; conversion alone is not evidence that removal is safe.

Teams membership and meeting Copilot

Set team owners deliberately and verify members. Standard channels follow team membership; private and shared channels introduce separate membership boundaries. Their files can reside in separate SharePoint sites, so review the actual channel site. For meeting Copilot, distinguish the administrator's meeting policy, the organiser's meeting option and whether transcription actually starts. If a saved transcript is mandatory, use the enforced saved-transcript policy mode, not a changeable default. Permission to transcribe does not start transcription. Validate the organiser and transcription starter's policies, licensing and supported meeting experience.

SharePoint permissions versus discovery

A group-connected team site and a communication site support different collaboration patterns. Review owners, members, visitors, direct grants and sharing links. Test a permitted person and a denied person. Restricted content discovery (RCD) reduces broad discovery; it does not remove underlying access and has documented exceptions. Restricted access control (RAC) adds a group boundary: a person needs both an allowed-group membership and underlying resource permission. Membership alone does not grant access. Microsoft Search and site exclusions govern discovery; they are not permission repairs. For Copilot data readiness, remove excessive permission and risky links before relying on search restrictions. Check the current SharePoint Advanced Management entitlement and scope for the chosen control.

Worked case

Requirement: only Finance should access a site. Mia has a sharing link but is not in a RAC allowed group. Ravi is in that group but has no site permission.

Result: neither condition set is complete. Mia fails the group boundary; Ravi lacks underlying permission. Give Ravi only the required site permission if approved. Do not add Mia merely to make her link work.

Requirement: every Sales meeting must preserve a transcript for later Copilot use. A default that organisers can change does not enforce this requirement.

03. Identity lifecycle and least privilege

An identity is an account or principal used to act. Authentication proves who it is; authorisation decides what it can do. An owner manages an object, a role permits administration, and resource membership grants access. Keep these relationships separate.

Users, guests, contacts and groups

Create users with the correct account details, location and service entitlement. Guest invitation creates a collaboration identity; cross-tenant settings govern trust and inbound or outbound collaboration. Invitation acceptance does not automatically grant a site. A contact is a directory entry for communication, not a sign-in account. Microsoft 365 groups support collaboration resources; security groups support access assignments. Dynamic membership is evaluated from a rule, while assigned membership is explicitly maintained. Choose the group type needed by the target service. For departures, block the relevant sign-in, address sessions and permissions, and preserve business data according to the approved lifecycle. Deleting immediately can break recovery and ownership.

Roles, PIM and administrative units

Choose the least privileged role that can perform the task and check its scope. An administrative unit (AU) scopes supported administration of member objects; it does not create a SharePoint data boundary. PIM eligible assignment is a right to activate a privileged role when required, rather than permanent active administration. Check activation requirements, approval, duration and audit. Test with the intended administrator, because an existing broad role can hide a scoping error. Assigning a team owner is not equivalent to giving a tenant-wide admin role.

Bulk work with Graph PowerShell

Connect to the intended tenant with approved scopes and the correct delegated or application permission model. Select only required properties and retrieve all pages where necessary. Inspect a sample before changes. For a CSV operation, validate headers, unique identifiers, blanks and duplicates; target object IDs rather than display names. Record one result per item. A successful script exit does not prove every row succeeded. Handle service throttling using the documented retry guidance; do not repeatedly replay a partially completed batch without checking results. Separate read-only inventory, proposed changes and the execution step.

Worked case

A regional support lead must manage only users in Region West. The lead already has a tenant-wide role.

First remove the misleading test condition in a controlled lab: use an administrator whose only relevant assignment is the scoped role. Put intended users in the AU and validate a permitted West action and a denied East action.

A 40-row import reports 38 successful updates and 2 duplicate identifiers. Record 38 successes and repair the two rows. Do not report 100% completion because the process ended.

04. Authentication and Conditional Access

Registration, authentication and policy enforcement are separate. A registered method might not be allowed for the user or suitable for the requested authentication strength. A missing MFA prompt does not establish that MFA was skipped.

Choose the identity control

Authentication-method policies control allowed methods and targeted users. Password Protection addresses weak or banned passwords; it is not an MFA policy. SSPR lets eligible users recover their account using configured methods. Check SSPR scope, method requirements and registration. Hybrid password writeback has additional configuration and licensing requirements; cloud reset success does not prove an on-premises password changed. ID Protection adds risk evidence and risk-based decisions; distinguish user risk from the risk of a particular sign-in. A reset, stronger authentication and access block are different responses.

Read a sign-in in the right order

Identify user, resource, client, timestamp and final result in Entra sign-in logs. Review Authentication Details and each Conditional Access policy result. Then inspect scope, exclusions, conditions and state. Report-only records a potential result without enforcing it. What If helps predict policy applicability, but a real event is better evidence of what occurred. An existing token claim can satisfy MFA without a new prompt. Allow time for logs to finish aggregating before declaring missing evidence.

Combine policies correctly

All applicable policies must be satisfied. A blocking policy wins over a policy that would permit access after MFA. A policy excluded from the relevant client category is not applied. Legacy authentication cannot fulfil modern MFA or device requirements; an applicable requirement can therefore block the request. Pilot changes with carefully scoped test identities and preserve a tested emergency access approach. Do not resolve an unexplained denial by excluding everyone from the policy.

Worked case

Fixture: sign-in succeeds; policy P1 requires MFA and succeeds; Authentication Details says the requirement was satisfied by a token claim; P2 is report-only and would require a compliant device.

Verdict: the event supports MFA satisfaction. P2 did not enforce device compliance. A screenshot showing no prompt does not reverse either finding.

New fixture: P1 succeeds, but an applicable P3 blocks access. The request fails. Combining policies is not a vote or a priority contest.

05. Defender policy and incident decisions

A policy specifies protection. A rule scopes who receives it. An alert signals something to investigate; an incident relates evidence. A delivery event, a user click and a compromise are different stages.

Choose protection and effective policy

Anti-spam handles unwanted mail; anti-phishing addresses phishing and impersonation; anti-malware addresses malicious attachments. Safe Links examines supported links, and Safe Attachments evaluates supported attachments. For recipient-based precedence, Strict preset precedes Standard, followed by applicable evaluation policies, custom policies and built-in/default protection. Within custom policies, a lower priority number wins. The applicable policy for a feature is used; settings are not merged across all matches. Check recipient inclusions and exclusions before comparing precedence. Custom priority zero does not outrank an applicable Strict preset.

Investigate before closing

In Defender, inspect the alert's affected user and message, relevant timestamps and related evidence. Trace receipt, protection action, delivery location, later remediation, user action and related account activity. Use message identity and recipient evidence to avoid confusing two similar subjects. Containment may include supported removal, quarantine or account protection actions according to the case. Check action status and remaining exposure. A submitted remediation request is not proof that all affected items were removed. Automated investigation helps collect and propose actions; review its evidence and approvals. Keep false-positive conclusions separate from lack of visibility.

Run simulations as training

Attack simulation training measures behaviour in an authorised exercise. Define audience, scenario and training assignment before launch. Review delivery, interaction, completion and repeat risk with the correct denominator and reporting period. A simulated click indicates training need; it is not evidence of a real compromise. A lower reported click rate can reflect a different audience or incomplete delivery. Verify those factors before claiming an improvement.

Worked case

A mailbox matches Strict and a custom anti-phishing policy with priority 0. The custom policy permits a sender that Strict treats differently.

Decision: first verify recipient scope. If Strict applies to the recipient and feature, its settings govern. Editing the custom priority cannot make it win.

An alert says a malicious message was delivered. A later removal action is pending. The case remains open for exposure and completion checks; pending is not remediated.

06. Purview: classify, prevent and retain

Classification identifies data. Protection controls permitted use. DLP applies rules to risky activity. Retention manages how long content is kept or deleted. Choosing one does not automatically achieve the others.

Classification and publication

A sensitive information type (SIT) detects a defined data pattern with supporting evidence and confidence. A sensitivity label classifies content and may apply configured protection. A label policy publishes labels to selected users and governs available labelling behaviour. Creating a label does not make it appear for every user. If a label is missing, check publication scope, supported client and propagation before changing its protection. If a document is accessible unexpectedly, examine permissions and the actual label settings; a label name alone proves neither encryption nor restricted access.

Specify DLP precisely

Write location, detection condition and supported action. Exchange concerns mail flow; SharePoint and OneDrive concern files and sharing; Teams concerns messages; Endpoint DLP needs onboarded devices. Do not substitute a Teams message rule for a file stored in SharePoint. For Copilot, choose a custom, Copilot-only policy. Distinguish restricting labelled grounding content, blocking supported sensitive prompt text and blocking a sensitive web search. Simulation records matches without blocking. The prompt-processing action is preview and tenant-dependent; verify support. Directly typed text and uploaded file content are not the same detection input.

Respond to alerts and monitor AI posture

Inspect policy, rule, location, matched evidence, user or agent, activity time and action. Establish whether the policy was in simulation or enforcement at that time. A match is not a demonstrated leak, and a block is not proof that every other channel is safe. In DSPM, use supported AI activity and findings to identify sensitive-data exposure and prioritise investigation. Correlate with audit and the relevant workload. Record coverage gaps, owners and follow-up instead of treating an empty dashboard as universal safety.

Retain content for the required lifecycle

A retention policy applies lifecycle settings across scoped locations. A retention label attaches lifecycle settings to an item, including supported record behaviour when configured. A retention label policy makes labels available or applies them through supported methods. Identify required duration, start event, location and disposition process. Preservation and deletion can interact with other policies and holds; test the effective outcome with the appropriate specialist. Sensitivity labels describe handling and protection; retention labels describe lifecycle. Backup is a recovery service, not a substitute for a legal preservation requirement.

Worked case

Requirement: stop financial account numbers typed into a supported Copilot prompt, while retaining Exchange coverage. Use a separate Copilot policy and Exchange policy with suitable conditions and actions.

A simulation event reports the prompt match and the user still receives a response. That is consistent with simulation. Verify tenant support, enforcement state and propagation before expecting a block.

Requirement: classify contracts as Confidential and keep them for seven years. Specify protection and retention separately; the word Confidential does not define seven-year retention.

07. Copilot readiness and user settings

Copilot readiness has four gates: entitlement, supported application experience, connectivity and governed data. A missing button and an unsafe answer are different problems. Diagnose the gate before changing settings.

Pilot the actual user experience

Select users with a real task and verify prerequisites for that Copilot experience. Check product licence, service availability, app version, signed-in account and applicable settings. Inspect excessive sharing in the data the task will use. Copilot can expose discoverable information that the user already has permission to access; repairing permissions matters. Pilot with both a permitted and a denied user. A successful answer proves only that task, identity and moment. Compare expected sources with grounding evidence and document failures.

Match tenant settings to the requirement

Use the Copilot settings experience for relevant tenant options and the applicable policy service for user settings. Separate self-service purchasing, admin-centre Copilot, release preference, AI disclaimer, video/image generation, search experience and web search. A disclaimer informs users; it is not a data-access control. Microsoft 365 Copilot Search concerns enterprise discovery; web search introduces external grounding. A product setting should be checked in the requested experience and for the requested audience, not inferred from another Copilot surface. Follow current supported values and role requirements rather than memorising a menu position.

Manage Cowork and providers

Cowork access uses current spending-policy controls selecting Cowork, with product prerequisites. The old Cowork registry entry is not an access switch. Web-search behaviour is controlled separately. Test fresh requests after propagation and distinguish user-targeted controls from device settings. For an external AI provider, evaluate the specific offering, legal processing relationship, region commitments, data flow and approved tasks. A provider brand or a tenant toggle does not prove every offering has the same privacy terms. Document approval and test the actual permitted experience.

Worked case

One licensed pilot user can use Copilot in the web experience but cannot see it in the desktop app. Another can use the app but sees overly broad project data.

These are different gates. For the first, inspect client, account and experience prerequisites. For the second, investigate resource permissions and sharing. Buying extra licences does not fix either observed issue by itself.

The business approves internal-only answers. A disclaimer is insufficient. Use the relevant web-search control and test the supported experience; review source evidence rather than judging by how an answer sounds.

08. Connectors and enterprise search

A connector brings another source into the search or AI experience. Content retrieval, identity mapping and access control must all work. A connected source can be available technically while still failing the user's permission requirement.

Select the retrieval model

A synced connector indexes source content and access information for later retrieval. A federated connector retrieves supported data at query time rather than maintaining the same content index. Its runtime call can still transfer data. Choose by freshness, source capabilities, permission model and permitted data flow. Do not assume that federated means no exposure or that synced means every employee can read everything. A search exclusion changes discovery; it does not revoke direct source access.

Validate source permissions end to end

Check the connection identity, required source permissions and mapping from source identities to Microsoft 365 identities. Verify crawl status, indexed items and expected access rules. A successful crawl proves ingestion, not permission correctness. Test one permitted person and one denied person using the same source item. For synced connector ACL changes, follow the required full-crawl process; an incremental content crawl is not proof that updated access rules were reprocessed. A failed connection can leave older indexed content available, so deletion or cleanup may require a separate action. For federated retrieval, test the runtime authorisation and returned content under the intended user context.

Troubleshoot relevance without weakening access

When results are missing, trace source availability, retrieval model, mapping, crawl/runtime result, permissions and discovery settings. Check query and supported result type after access prerequisites. Do not make the source public as a relevance test. When results are stale, check indexing or runtime cache behaviour and last successful refresh. Record the source item, identity, query and timestamp so another administrator can reproduce the issue.

Worked case

A synced CRM connector crawled successfully yesterday. Today a source ACL removes Lena. An incremental content crawl succeeds, but Lena still gets the old result.

Decision: verify the source ACL and mapping, perform the supported full crawl for ACL changes and test Lena again after processing. Do not conclude that removing the source permission instantly updated the index.

A federated source is queried live. The architecture avoids a persistent content index, but the response still enters the supported AI workflow. Include that transfer in the approval.

09. Agent identity, access and registry

An agent is an actor that can retrieve information or take supported actions. Approving its listing, assigning its identity and granting it resource access are separate decisions. Identify the actor at each step.

Know the object model

An Entra agent identity blueprint defines the agent application pattern; its blueprint principal represents it in the tenant. Child agent identities represent runtime agents. Some agents also have a paired agent user for supported user-account scenarios. A human sponsor or owner is a different object. Record object IDs and relationships. Do not treat a paired user as identical to the runtime agent identity. Manage ownership and lifecycle so departures do not leave orphaned agents. Inventory, approve, operate, review and retire with resource grants and credentials accounted for.

Govern resource access

Access packages manage approved business-resource access with supported approval, duration and review controls. They are not Agent 365 security templates. In Entra, find the agent identity, open its Access packages view, inspect the assigned package and enabled policy, review actual resources and roles, and save only the approved changes. Test the intended resource and an out-of-scope resource. Check support and entitlement for agent identity governance in the current tenant. A package assignment is evidence of configuration, not proof that every API call is correctly authorised.

Apply Conditional Access to the actual subject

Blueprint-targeted agent policies can scope supported child agent identities; paired user accounts require their own appropriate targeting. Agent identity policies use supported block controls rather than an interactive human MFA challenge. Verify fresh token requests after propagation. An API-key call that bypasses Entra authentication is outside that token policy path. Record authentication method, subject, target resource and policy result when assessing coverage. A green user sign-in test is not evidence of agent-token enforcement.

Review agents and their tools

In the registry, inspect publisher, purpose, owner, requested capabilities, data access and status. Review requests, publish or reject, then control installation and user access as required. Set allowed types, sharing and template defaults deliberately. An approved agent is not automatically approved for every tool. Tool registry and requests support separate review of available capabilities, publishers and block status. MCP provides an interface to tools and data; it does not establish trust or least privilege. Custom upload or BYO tool support requires checking current format, preview status and onboarding prerequisites. Reassess agents after a capability or ownership change.

Worked case

A procurement agent has an approved listing, a paired user and a runtime identity. Its package permits the Procurement site only. A new tool requests access to all projects.

Decision: approval of the listing does not justify the new grant. Review the tool separately, identify the token subject and narrow resource permissions. Test Procurement success and HR denial.

A blueprint block stops new child-agent token requests, but a paired user can still sign in. This does not prove the blueprint block failed; the two subjects require separate evidence and scope.

10. AI monitoring, cost and exam decisions

The right report depends on the question. Usage is not business value. An audit event is not an adoption trend. A spending alert is not necessarily a service stop. Match platform, population, time and measurement before drawing conclusions.

Choose the evidence source

Use Microsoft 365 admin usage reports for eligible user and workload activity. Use supported Copilot dashboard insights for adoption patterns in the available population. Use Purview Audit for an individual supported activity; a Copilot interaction record does not guarantee verbatim prompt text. Use Copilot Studio analytics for its environment and agents. Use Azure monitoring and Cost Management for the relevant Foundry resource. Agent 365 overview and registry views help assess the agent estate. Copilot Control System helps bring administration, usage and service health views together; check scope and freshness rather than assuming every AI platform is in one report.

Investigate agent governance gaps

Correlate owner, identity, tools, permissions, activity, sensitive-data findings and action status. If an agent accessed a protected resource, inspect the actual principal and token path, source permission and supported data controls. Do not declare compliance from registration alone. Record the gap, affected resources, risk evidence, accountable owner and corrective test. A missing event may reflect unsupported activity, reporting delay or insufficient visibility. State the limitation instead of inventing a safe outcome. Service health should match the failing service, geography and time; compare a product incident with individual request failures.

Reconcile cost before optimising

Separate assigned licences, prepaid/capacity funding and metered pay-as-you-go. For Microsoft 365 spending policies, inspect per-user and total limits, targeted group and period. Where multiple policies apply, current precedence chooses the highest per-user limit, then highest overall limit, then the newest policy. Moving a user does not erase already consumed usage in the same period. Supported enforced limits can stop covered service access; Azure budgets normally notify and do not stop the resource. Reports refresh at different times. Compare the same UTC period, currency, resource and meter. Copilot credits or tokens are consumption units, not currency. Avoid counting a charge twice when it appears in both Microsoft 365 and Azure reporting.

Measure adoption honestly

Define eligible population, active users, workload, window and refresh time. Fictional example: 60 active users out of 100 eligible users is 60% adoption; 60 out of 80 licensed users is 75% of licensed users. Both calculations are valid only with their stated denominator. A dashboard's estimated time saving is a modelled measure, not proof of causal return on investment. Compare similar groups and workload opportunities before recommending removal or expansion. Optimise unwanted consumption and poor task outcomes, rather than simply maximising activity.
